# Task spec

## 背景

后台 `omni_panel serve`(父进程 spawn 子进程 + 轮询 cli.json)在旧实例关闭空窗内启动时,子进程因 Electron 单实例锁冲突 `requestSingleInstanceLock()` 失败 → `app.quit()` 以 **code 0** 静默退出,且发生在日志初始化前 → 子进程 serve 日志 0 字节。父进程轮询 `background_serve.ts` 只认 `exitCode !== 0` 为失败,把 code-0 早退当「仍在启动」,空等 15s 后误报「等待 serve 启动超时」,无诊断信息。来源 `p209`(2026-09-04 核实,含受控复现)。

## 契约区

### 范围

- 后台 `serve` 父进程等待逻辑(`src/main/cli/background_serve.ts`)识别子进程 code-0 早退:退出即失败,不空等 15s。
- 失败/超时诊断提示补足单实例锁冲突场景,让用户可自解。
- 覆盖上述行为与 code-0 / 非 0 早退分支的自动化测试。

### 非范围

- 不改 `serve --foreground`、GUI 启动、瘦客户端(quit/status 等)路径。
- 不改单实例锁的获取策略(`requestSingleInstanceLock` / `app.quit`),不引入锁排队。
- 不改 `index.ts` 启动流程其它部分。
- 不做 `p209` 之外的生产修复。

### 风险与回退

- 风险：改父进程退出判定可能误伤「正常启动但较慢」场景——若子进程存活却超过 15s 未写 cli.json,保持现超时路径;本改动只把「已退出」从等待中剔除,不缩短存活子进程等待时间。
- 回退：改动集中在 `background_serve.ts` 一处与对应测试;git revert 该 task 提交即可。

- 平台:Linux(WSL)实测,锁冲突为 Electron 单实例机制通用行为;Windows/macOS 机制同源,不做平台专属分支。
- 不改 `src/main/cli/background_serve.ts` 之外的生产文件;不改单实例锁策略。
