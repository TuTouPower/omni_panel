# Task spec

## 背景

花云单账号可挂多个服务，用量按服务分别计量。当前实现只取首个服务：`connectors/flowercloud/connector.ts` 用 `flower_product_details_id` 取页面第一个 `productdetails&id=`，只输出一条 `flowercloud:traffic`（`account_id` 固定 `flowercloud_default`）；宿主侧 `src/main/core/session/flowercloud_dom.ts` 的 `flower_snapshot_url` 同样只认首个 id 作为快照起始页。p267 已登记该缺口，连接器目前只加了一条多服务 `warn` 作为最小可感知措施。

## 契约区

### 范围

- 采集：解析页面中全部服务，每个服务输出一组用量指标，`account_id` / 标签可区分且不冲突。
- 失败隔离：某服务解析失败不阻塞其它服务输出。
- 快照与会话：快照能覆盖多服务场景（首页直达或在服务间导航），失败时旧值语义与 t535 一致。
- 展示：多服务在用量面板 / 弹窗中可区分服务名与各自用量。
- 若产品决定只支持单服务，则改为明确的产品决定：UI 明示「仅统计首个服务」及原因，并在本 spec 记录该取舍。

### 非范围

- 不改花云会话窗口与后台策略（t535）。
- 不做其它 provider 的多账号 / 多指标改造。
- 不改连接器通用账号模型（`account_id` 生成沿用现有约定）。

## 上下文区

- 来源：p267（核实：2026-09-29，连接器与宿主均只认首个服务 id；已加多服务 `warn`；无多服务 fixture）。

### 有意不测

- 真实账号的页面结构差异（不同产品类型的用量卡片布局）：无真实样本前不写断言。
- 服务级重置日差异：现有 `RESET_DAY` 兜底语义不变，不在本 task 扩展。

### 测试策略

- 新增多服务 HTML fixture（两个及以上服务的用量卡片），断言多观测输出、`account_id` 唯一、失败隔离。
- Web 层测试断言多服务卡片展示与标签。
- 回归：单服务 fixture 行为不变（现有集成测试保持通过）。

未核实的外部契约标为 `UNVERIFIED-BLOCKING` 或 `UNVERIFIED-SPIKE`；核实后改写为结论和验证方式。无则写“无”。

- 无未核实外部契约。原项「真实多服务账号的客户区 / 服务页 DOM 结构（服务列表与用量卡片的关联方式）」已由 spike `s041`（`docs/spikes/s041_flowercloud_multi_service_dom/`）验证为结论：**链接在卡/行尾的结构下卡窗切片可靠**（真实单服务样本同构 3 服务列表与 WHMCS 表格 probe 全 PASS，字段数值逐一断言）；**结构漂移（链接前置）表现为窗口缺失而非可自动识别的错配，故生产规则定为「任一服务窗口不完整 → 丢弃全部窗口结果、逐服务 HTTP 详情页补数，补数失败逐服务 `report_failed_account`」**。验证方式：`code/probe.mjs` 断言 + 落地为 t537 集成测试（fixture `clientarea_multi_sample.html` 等）。真实多服务账号的类型化布局差异维持「有意不测」。

### 风险与回退

- 风险：多服务导航增加快照耗时与失败面（会话窗口交互次数上升）；`account_id` 变更可能影响既有用户历史数据的连续性。
- 回退：保留单服务路径作为「只有首个服务」的退化形态；`account_id` 迁移需给出历史数据兼容说明。

### 依赖与约束

- 依赖 t535 对快照窗口与失败语义的收敛。
- `account_id` 若从 `flowercloud_default` 变为按服务生成，需评估历史观测与前端映射的兼容性。
