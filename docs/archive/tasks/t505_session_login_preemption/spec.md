# Task spec

## 背景

当 Session 类连接器凭据失效时，调度器会触发后台无头自动重登（`hidden: true`，30 秒安全超时）。在此期间，`SessionManager` 内部的一刀切互斥锁（`in_progress`）被该后台任务独占。
若用户在此时通过设置面板主动点击「网页登录」，系统检测到 `in_progress` 存在活跃会话，一律作为 `CONFLICT` 拒绝，弹出「已有登录正在进行中，请等待当前登录完成」，导致用户必须干等 30 秒超时才能操作。
该行为属于典型的**低优先级后台任务阻塞高优先级前台用户操作（优先级倒置）**。前台用户主动登录应当具备最高优先级，并能够立即抢占后台隐藏重登会话。

## 契约区

### 范围

- **`SessionManager` 锁模型升级**：将 `in_progress` 从无差别 `Set<string>` 改造为记录会话类型（是否为 `hidden`、窗口句柄、取消回调）的映射表；
- **前台交互登录抢占（Interactive Preemption）**：当收到可见登录请求（`!request.hidden`）时，若当前占有锁的会话为后台自动重登（`existing.hidden === true`），立即强制终止并销毁该后台隐藏窗口、释放锁，并无缝为用户启动可见登录窗口；
- **同级与前台并发防护保持**：若当前占有锁的会话本身已是前台可见窗口（`!existing.hidden`），用户再次点击仍正常返回 `CONFLICT` 拦截，防止重复弹出多个可见登录窗；后台任务之间的并发仍保持互斥；
- **`auth-ipc` 状态协同**：适配 `startCookieLogin` 与 `handleCookieLoginStatus`，仅后台隐藏会话运行时不阻断前台交互登录的启动；
- **自动化测试**：补齐前台抢占后台隐藏会话、前台互斥、后台互斥及抢占后凭据落库全链路测试。

### 非范围

- 不修改连接器指标采集、OAuth 登录或其他非 session 类认证方式。
- 不改变普通手动登录成功后的关窗与凭据落盘逻辑。

- [ ] AC-001：当后台隐藏重登会话（`hidden: true`）正在运行时，用户触发可见登录（`!request.hidden`）能够成功启动并打开可见窗口，不再抛出或返回 `CONFLICT`（`已有登录正在进行中`）。

- [ ] AC-005：抢占发生后，前台可见登录窗口正常捕获 Cookie/凭据并写入 Vault，后续用量采集能够使用该新凭据正常恢复。

## 上下文区

- 来源：用户实测问题（t504 引入后台隐藏重登后，用户手动点击「网页登录」被报 `已有登录正在进行中，请等待当前登录完成`）。
- 既有设施：
    - `src/main/core/session/session-manager.ts`（`in_progress` 锁与 `start_login` 生命周期）
    - `src/main/ipc/auth-ipc.ts`（`startCookieLogin` 与 `handleCookieLogin`）
    - `src/main/ipc/session-ipc.ts`（`session:login` IPC 分发）
- 相关历史 task：t278（Web 认证对齐）、t337（OpenCode 有效性探测）、t504（统一 Web 会话保活管线）。

### 有意不测

- 外部站点的真实人机交互登录过程（验证码/扫码等）：以 mock/fake BrowserWindow 与 webRequest 事件覆盖。

### 测试策略

- 单元测试：扩展 `tests/unit/session/session-manager.test.ts` 覆盖抢占后台隐藏窗口、前台互斥、后台互斥及生命周期。
- IPC 测试：扩展 `tests/unit/ipc/auth-ipc.test.ts` 断言前台触发时即使后台在跑也能成功启动。

### 风险与回退

- 风险：抢占发生时若旧窗口的 webRequest 监听或定时器未及时解绑，可能出现迟到的请求干扰新窗口。
- 回退：在取消旧会话时严格执行 `clear_timers`、`window.close()` 并标记 `completed = true`，忽略所有后续回调。
