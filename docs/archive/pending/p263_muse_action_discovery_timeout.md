# p263 Muse 动态 Action 发现串行下载全部分包，超出宿主 15 秒预算

- 类型：bug
- 处理：t530
- 核实时间：2026-09-27T06:41:35+08:00

## 现象与影响

用户反映 Muse 多次修复后仍显示采集失败。运行日志显示，刷新不是收到服务端认证错误或 Action ID 404，而是连接器执行达到 15000ms，被隔离进程看门狗强制结束；三次尝试失败后，原有两条 observation 被标记 stale，实例进入 failed。

影响 Muse 用量与额外额度更新。非基准部署进入动态发现路径后，首页资源数量与累计请求时延可能超过宿主执行预算；重试重新开始下载，不能复用上一轮进度。界面保留旧数据但不能恢复新鲜度。

当前运行应用位于 `artifacts/mac-arm64/OmniPanel.app`。运行包中 `Contents/Resources/connectors/muse/connector.ts` 与仓库源码经 `cmp` 比较一致，排除本次连接器修复未进入运行包这一解释；此比较不代表对整个运行包版本作出一致性保证。

## 最小诊断与实测结果

材料：

- `.scratch/muse_timing_probe.mjs`：读取当前 Muse vault 凭据，仅在内存中解密；使用应用日志确认的系统代理访问 Muse 原站。经 TypeScript 转译、VM 执行现有生产连接器 `main()`，在 `ctx.http` 适配层记录每次请求耗时。
- `.scratch/muse_timing_probe.jsonl`：请求方法、路径、状态码、响应字符串长度、累计耗时及最终指标数量。不记录 Cookie 或响应正文。

执行：`node .scratch/muse_timing_probe.mjs > .scratch/muse_timing_probe.jsonl`。此命令访问真实站点，应仅在有必要核实变化时使用，不作为常规离线测试。

|阶段|实测结果|
|---|---|
|首页 GET|HTTP 200；单次约 1313ms|
|累计约 18 秒|仍在下载 JS 分包，第 71 次 GET 开始，用量 POST 尚未发出|
|发现 Action|107 次 GET（首页与分包）完成后，累计 27006ms 才成功解析 Action ID|
|用量 POST|累计 27006ms 发出，27535ms 收到 HTTP 200|
|解析完成|累计 27536ms，成功返回两条 observation|

全程 108 个 HTTP 响应均为 200。探针字段 `bytes` 实际记录 JavaScript 字符串 `.length`，不能解释为精确网络传输字节数。

验证边界：这是生产连接器逻辑的真实网络诊断，HTTP 由 undici 适配，诊断外层允许执行超过 15 秒，并非完整生产 NetClient/隔离宿主重放。应用日志证明生产执行被 15 秒预算终止；探针证明相同连接器在当前会话、代理与站点资源条件下，完成串行发现需要约 27 秒。两者共同支持本次超时机制，但不保证每次请求耗时固定。

## 根因与历史修复关系

分类：产品实现与运行预算不匹配。

1. `connectors/muse/connector.ts` 的 `resolve_dynamic_action_ids()` 在无法使用基准部署捷径时，从首页提取脚本列表。
2. `for (const s of all_scripts)` 内逐个 `await ctx.http.get_raw()`，先下载所有首屏脚本，之后才扫描 `fetchSubscriptionAction` 或设置组件异步分包。即便某个早期响应已包含足够线索，也不会在下载阶段提前结束。
3. 发现完成后才发用量 POST。没有跨刷新复用发现结果；失败重试也会从头重复此工作。
4. `src/main/core/scheduler/refresh-service.ts` 为隔离执行传入 `DEFAULT_TIMEOUT_MS`；`src/shared/constants.ts` 定义为 `15_000`。`isolated-process-runner.ts` 在总预算到期后终止进程。
5. 实际百级串行请求耗时已经超过 15 秒，不需要单个请求卡死或解析异常，也足以稳定触发此次失败。

此前 t525 修复动态 Action ID 发现与会话误判，但动态发现的真实请求规模未纳入验收。已有黑盒成功记录只证明当次环境可用，不能覆盖后续部署变化触发完整扫描时的性能与预算。

本次探针使用现有 Cookie，最终用量 HTTP 200 且产出两条指标，证明本次会话与响应解析可用；不能据此承诺 Cookie 永不过期，也不能证明所有未来网页部署结构都可解析。

## 同类位点扫描

- Muse 首页脚本下载循环：已确认主问题。
- Muse `target_chunks` 异步分包下载循环：同样串行，占用同一发现与采集预算，应纳入同一修复验证范围；不单独断言它贡献了本次全部延迟。
- Muse 每轮刷新与失败重试：重新执行发现逻辑，未复用已经成功解析的结果，放大请求成本。
- 其他连接器：按 `get_raw`、`script_contents`、脚本列表循环检索，未发现相同首页全量分包扫描实现；此结论限于该模式，不代表其他连接器没有超时风险。

## 测试缺口与补测方向

现有 `tests/integration/connector/muse_connector.test.ts` 覆盖动态 ID 提取、异步模块链接、ID 边界、参数覆盖和响应解析，但动态场景仅少量模拟分包，`Promise.resolve` 立即返回。测试证明解析行为，未证明真实规模下能在宿主预算内完成。

建议新增触达生产逻辑的回归：

- 百级分包与可控延迟：验证发现和用量请求能在约定总预算内完成，且不会无条件下载全部无关资源。
- 隔离宿主预算：覆盖真实 runner 总超时与连接器网络阶段之间的关系，不能只测单次 HTTP 超时。
- 提前命中、无命中、单分包失败与慢响应：验证停止条件、错误可观察性，以及用量请求不会因发现阶段耗尽预算而永远无法执行。
- 若采用复用机制，覆盖同部署再次刷新、部署变化失效、服务端拒绝旧 Action 后重新发现；不能让旧 ID 永久掩盖发现失败。
- 若采用并发，验证请求并发有上限，成功或超时后不遗留无界后台请求。

原有解析与认证语义测试应保留；不将测试预期修改为当前超时行为。

## 修复方向与验收建议

具体方案由修复 task 确定。优先减少无关下载、命中后停止、合理限制并发，并评估按部署复用成功发现结果；发现阶段与用量 POST 应共享明确的总预算，保留足够时间完成实际采集。补充阶段、请求数量与耗时日志，禁止记录 Cookie 或完整页面。

单纯提高 15 秒上限会保留每轮百余请求与重复下载成本，不能独立作为完整修复。仅再次更新硬编码 Action ID 也无法解决下次部署触发扫描后的超时。

验收至少覆盖：部署变化后自动取得新 Action；首次发现和后续刷新均能在约定预算内产出真实用量；网络失败和发现失败有准确可诊断错误；凭据与页面敏感信息不落日志。涉及打包真实刷新验证时，按项目规则事先取得重启/打包许可。
