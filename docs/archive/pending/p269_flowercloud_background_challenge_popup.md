# p269 花云后台刷新遇验证自动弹窗，缺少自动处理与静默失败边界

- 来源：2026-09-29T21:09:54+08:00，用户反馈花云后台刷新自行弹出验证窗口，要求详细登记 pending todo。用户希望程序优先后台处理可自动完成的验证，不应把后台取数失败直接转成人工打断。
- 类型：bug，兼含后台自动处理能力缺口。
- 处理：t535, t536

## 现象与期望

花云用量依赖已登录网页的 DOM 快照。当前刷新遇 Cloudflare 质询、登录页或访问拦截页，等待一定时间后主动显示会话窗口；用户没有点击“处理验证”或“重新登录”，也会被要求前台操作。普通手动“刷新”同样可能触发这条路径，刷新意图与打开交互窗口意图未区分。

期望：先利用现有 Electron Chromium 会话能力在后台尝试自动恢复，包括评估可操作验证控件的自动交互。失败必须有界退出，保留最后成功数据、明确标记过期及原因、提供用户主动处理入口。只有用户主动选择处理验证或登录，才允许将交互窗口展示到前台。

“能模拟点击”与“服务端最终接受验证”必须分开。尚未验证真实花云 Cloudflare 控件能否定位、交互、通过；不能承诺无头浏览器必定能过，也不能仅凭识别到验证页就断言必须人工。登录过期和访问拦截也不等于勾选验证框即可解决。

## 当前触发链路与代码证据

4. `src/main/core/session/flowercloud_dom.ts:384` 复用并补种 cookie、加载页面；`poll_flower_usage_html` 轮询 HTML，分类页面。`flower_needs_user`（第 156 行）把 `cloudflare`、`login`、`blocked` 都归为需要用户的页面。

6. `src/main/index.ts:792` 的 `reveal()` 执行 `setOpacity(1)`、恢复任务栏参与状态（非 macOS），然后 `window.show()`。这是主动将窗口转为可见的明确调用；操作系统实际焦点效果尚未真机验证。
7. 当前后台动作包括页面加载、读取 HTML、概览页导航到服务详情、等待页面变化；未发现定位验证控件、自动点击、读取交互结果并决定重试的实现。单纯轮询不等于已经尝试自动勾选。

以上位置以登记时未提交工作区为准，后续修改可能使行号变化。

## 窗口生命周期与影响

- 自动刷新会把取数失败升级为前台交互，打断当前工作。触发范围包含三类阻塞页面，不限于 Cloudflare，也不是所有网络错误都会弹窗。
- 当前代码已经延长亮窗后的采集等待：`FLOWER_REVEAL_BUDGET_MS = 120_000` 加 `FLOWER_HANDOVER_WAIT_MS = 30 * 60 * 1000`，约 32 分钟；在此期间继续采集，并保留在途登记。此前讨论中的“亮窗后 120 秒即停止采集”已不符合当前代码，不能沿用。
- 最终等待预算耗尽且页面仍阻塞时，`flowercloud_dom.ts:414` 返回 `handed_over: true`；`session-manager.ts:638–648` 保留窗口，却删除 `flower_snapshots` 和 `in_progress`。此后本轮轮询已结束。静态路径表明再次刷新可创建新窗口，旧窗口仍存活；旧窗口晚到的验证完成也没有本轮 DOM 轮询继续接收。此尾部风险仍存在，不能因等待延长就视为消除。
- 等待期间刷新服务停在前置采集阶段，可能长期显示 `loading`；具体 UI 呈现与真实等待时长需要集成验证。
- 已存快照在失败路径保持不变。修复需确保 UI 同时说明旧数据年龄与失败原因，不能把旧值伪装成刚刷新成功。此次未验证全部 stale 展示链路，不将其另列为已确认缺陷。

### 已核对的具体代码路径与结论

已研究当前源码，确认存在“验证窗获焦后主面板隐藏”的条件性路径；日志已排除本次现象只是隐藏。**真实应用进程退出已确认，退出请求入口与根因尚未定位**，不能断言与主动弹窗同根因。以下代码位置属于当前工作区，不等同于事发时运行包。

1. 前台验证窗触发面板隐藏：`src/main/index.ts:792` 的 `reveal()` 调用 `window.show()`；同文件约第 1537 行的 `browser-window-focus` 处理非主面板窗口获焦，经 `should_hide_popup_on_outside_focus` 判断后调用 `main_panel_controller.hide()`。`src/main/core/main-panel/main-panel-controller.ts:55` 的条件严格为 `popup && panel_visible && !focused_is_panel && !pin_to_top`；约第 382 行的 `hide()` 最终调用 `win.hide()`，不退出进程。因此普通 popup 面板在未钉住时可能因验证窗获焦而消失；浮窗模式和钉住状态不适用此链路。用户现场是否满足这些条件仍未确认。
2. 登录取消、关闭与超时：`src/main/core/session/session-manager.ts` 约第 355 行的 `finish_with_error` 清理 timer、释放登记、只关闭对应登录窗口并 reject；约第 539 行的 `closed` 进入 `save_cookie_on_close`，约第 544 行超时进入 `finish_with_error`。快照路径约第 641 行的 `finally` 同样只处理对应窗口。已查路径未直接调用 `app.quit()`。
3. 上层错误处理：`src/main/ipc/auth-ipc.ts:151` 等待 `start_login`，约第 164 行 catch 转成失败 `IpcResult`；`src/main/core/scheduler/refresh-service.ts:421` 的前置快照 catch 与约第 681 行的重登 catch 记录错误。这里未建立“花云未登录 → 应用退出”的调用链。
4. 生命周期默认行为：`src/main/index.ts:1683` 的 `window-all-closed` 是空处理器，注释说明托盘保持应用存活；`src/main/bootstrap/cli_init.ts` 约第 19、24 行的异常与 Promise rejection 处理仅记录日志，不主动退出。不能据“最后窗口关闭”直接推导整应用退出。
5. 已扫描的显式退出入口：`src/main/index.ts` 约第 912、915 行是控制接口的 restart/quit，约第 1436、1440 行是托盘 quit/restart，约第 1634 行是在既有 `will-quit` 清理后再次 quit，约第 1654 行的 `app.exit(1)` 位于启动失败 catch；`src/main/menu/application-menu.ts:49` 是显式 Cmd+Q 退出。当前没有证据把花云未登录连接到这些入口。以上行号按本次代码分析时工作区记录，后续变更可能偏移。

## 根因与同类扫描

根因属于产品交互策略与会话生命周期缺陷：页面分类直接绑定前台 `reveal`，没有“后台刷新是否获准进入交互模式”的边界；自动恢复仅等待页面自行完成，缺少主动交互能力评估与明确失败出口；最终保留窗口与释放任务登记不同步。

同类扫描结果：

- 同一个 `flower_needs_user` 分支覆盖 `cloudflare`、`login`、`blocked`，三类均纳入修复与测试范围。
- 已扫描 `src/main/core/session` 与 `src/main/index.ts` 的 `reveal` 调用，花云轮询最终使用同一个宿主显示实现；不是另一个独立自动弹窗入口。
- 定时/普通刷新与强制刷新共用快照调用；两者只在是否跳过新鲜快照上有区别，不能把强制刷新视为用户已同意打开验证窗口。
- 通用自动重登已有 `hidden` 语义；本次未确认其他 provider 存在同样的主动 `reveal` 问题，不扩为全 provider 改造。
- `p268_flowercloud_snapshot_window_macos.md` 记录透明采集窗口在 macOS 仍可能出现在窗口层级的问题；本条关注主动 `reveal/show` 与验证处理策略，跨平台成立。两者可关联，但不能互相替代。
- `p267_flowercloud_multi_service_usage.md` 关注多服务用量，和本条不同，不合并、不修改。

1. 定时刷新、自动恢复和普通“刷新”操作遇阻塞页，不自动显示窗口或抢焦点；交互窗口只能由明确的用户处理动作打开。
