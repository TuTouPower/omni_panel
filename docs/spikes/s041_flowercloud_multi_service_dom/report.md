# Spike report

## 问题

花云多服务账号的客户区/服务页 DOM 结构中，「服务列表与用量卡片的关联方式」未核实（t537 spec 原 `UNVERIFIED-SPIKE`）：能否从一页列表 HTML 中按服务切分出各自的名称/用量/重置日，且不错配？

## 成功判据

- 构造的 WHMCS 同构多服务列表页上，「卡窗切片」能按服务 id 分离出各自字段且数值正确。
- 结构不满足假设（链接不在卡尾）时，行为是**可检测的缺失**而非静默错配，足以驱动 HTTP 逐服务详情页兜底 + 显式失败登记。

## 尝试

- 无真实多服务账号样本，按 spec 允许的替代路径「按 WHMCS 结构构造 fixture 并验证」执行。
- `code/clientarea_multi_sample.html`：以真实单服务样本 `tests/fixtures/connector/flowercloud/clientarea_sample.html` 的卡结构（产品名 → 用量 → 日期 → 详情链接）同构扩展为 3 服务卡列表。
- `code/whmcs_table_sample.html`：WHMCS 默认产品表（每行链接在行尾）2 服务。
- `code/probe.mjs`：复刻 `connectors/flowercloud/connector.ts` 的 `extract_from_html` 正则，实现「按详情链接位置切窗（第 k 窗 = 第 k-1 链接末尾到第 k 链接）」原型，对三份 HTML 断言；另构造链接在卡首的反例。

## 证据

`node code/probe.mjs` 全部 PASS：

- 三服务卡列表：id `8848/8849/8850`、名称 Lite/Plus/Max、用量 `34.56/150`、`77.1/400`、`1228.8/2048`（1.20TB/2.00TB 换算）、重置日 `2026-10-18 / 2026-11-05 / 2026-10-02` 均正确。
- WHMCS 表格：id `9901/9902`、用量与名称正确。
- 链接卡首反例：第 1 窗缺失（miss），第 2 窗「命中」但带的是第 1 个服务的 `10/150` —— **错配被实测确认**。

## 结论

1. 链接在卡/行尾的结构（真实单服务样本与 WHMCS 默认表格均为该形态）下，卡窗切片可靠分离多服务字段；仅凭窗口「是否命中用量」无法识别错配（错配表现为命中）。
2. 因此生产规则必须是：**任一服务窗口不完整 → 丢弃全部窗口结果，逐服务 HTTP 详情页补数；补数失败逐服务 `report_failed_account`，绝不静默**。链接前置等结构漂移由此表现为显式失败而非错误数据。
3. 服务列表页本身取不到用量时，详情页（真实单服务样本已验证的结构）仍可解析；宿主快照侧配套策略：多服务列表一律从列表页发现全部服务 id 并逐服务详情页抓取（composite 分段快照），列表级快照仅作连接器 HTTP 兜底输入。
4. 限制：未见真实多服务账号样本；不同产品类型的用量卡片布局差异未覆盖（t537 spec「有意不测」）。可信度：构造样本上的算法行为已实测；真实结构同构性基于真实单服务样本外推。

## 是否采纳

- 决定：是
- 理由：卡窗切片 + 「不完整即全量 HTTP 兜底 + 显式失败」组合满足 t537 AC-001/002/003 的可测基础，且对结构漂移不产生静默错配。
- 后续 task：t537
