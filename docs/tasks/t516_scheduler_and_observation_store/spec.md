# Task spec

## 背景

调度服务与观测存储层存在性能退化与并发鲁棒性缺陷：刷新任务并发池异常未被捕获会导致剩余任务孤儿化或整轮失败；最小刷新间隔 5s 过于频繁且连续失败无退避；实例查询缺失复合索引导致全表扫描；stale 副本逐条 autocommit 写入低效；错误分类匹配过宽；趋势与日志查询无上限防护；数据过期清理在极端参数下死循环阻塞主线程；读数据无反序列化校验。

## 契约区

### 范围

- 修复 `with_concurrency` 并发控制原语，确保单项异常被隔离，正确从 executing 集合移除。
- 调度器最小刷新间隔提高至 30-60s，失败重试引入指数退避与随机抖动（jitter）。
- 数据库新增 `idx_by_instance` 索引并纳入 migration 版本管理。
- `insert_batch` 增加 `{ok, failed}` 返回状态；失败路径 stale 记录改为批量单事务写入，且严格只复制最新 `stale=0` 观测。
- 严密化 `is_connection_error` 的分类正则，杜绝业务报错误归类。
- 为 `query_trend` 设置 `days ≤ 365, cap ≤ 1000` 约束；数据保留清理引入 `DELETE ... LIMIT` 分批机制并设置下限保护。
- 事务化 Kimi purge 操作；将定时器 sleep 改为可使用 AbortSignal 中止的实现。
- 存储层读取引入 `safeParse`，遇到脏数据行记录日志并跳过。
- 查询改为显式列投影；token-stats 查询补充 LIMIT/offset 分页。
- 集中抽取刷新参数常量；记录动态扩界日志；显式固化 `force` 刷新语义。

### 非范围

- 不修改现有图表与上层视图展示的业务指标定义。
- 不替换 SQLite/better-sqlite3 底层库。

- [ ] AC-001：`with_concurrency` 队列中某项任务 Promise reject 时，正在并发的其他任务不受影响，队列完整执行完毕。
- [ ] AC-002：调度器遵循不小于 30s 的刷新周期下限，遇到连续采集失败时下次间隔按指数递增且附加随机抖动。
- [ ] AC-003：执行按 instance 查询时命中数据库 `idx_by_instance` 索引，避免全表扫描。
- [ ] AC-004：采集失败后由单事务批量写入降级副本，且仅基于最新成功记录进行复制，无多轮 stale 衍生雪崩。
- [ ] AC-005：`query_trend` 输入超出范围的参数时自动钳制在有效范围内，查询结果不超过指定数量上限。
- [ ] AC-006：数据清理在空间极度紧张时每次分批删除固定行数，避免长时间独占数据库锁导致主线程卡顿。
- [ ] AC-007：应用退出时调度休眠立即解除，关闭过程平稳无拖延。

### 风险与回退

- 风险：提升刷新最小间隔可能让期望频繁自动刷新的用户感知到数据更新周期延长。
- 回退：手动刷新通道（force）不受该下限限制，可随时主动刷新；必要时微调配置参数。
