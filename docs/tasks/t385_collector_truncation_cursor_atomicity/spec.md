# Task spec

## 背景

collector 单源 sessions/daily 总数超 `MAX_RECORDS` 时，每轮只入列前 10000 条。t345 引入跨轮截断游标（`source_cursors`）后，单进程内截断数据可跨轮推进不丢；但游标**仅内存、按排序位置计数**：a) 未入 scan-state，跨重启归零——超限源只重复发前 10000 条，之后数据在「重启频率高于截断发完所需轮数」时实际永久不发；b) 按 `session_id` 排序位置跳过（reader `[...dirty].sort()`），新会话排序在游标前会被计入跳过而永久漏发；c) postMessage 失败时游标随扫描状态一并回滚（collector.ts:635），截断轮重扫重发，工作重复但幂等。与 postMessage 失败回滚同源：扫描状态与 emission 原子性。p163 已核实（2026-08-15），建议单列本 backlog 统一设计。

## 契约区

### 范围

- `src/main/core/collector/` 下统一设计「扫描状态与 emission 原子性」：
    - `source_cursors` 截断游标持久化（入 scan-state，跨重启保留推进进度）
    - 截断推进改 identity 式（按已入列 key 记账而非排序位置，新会话排序在游标前不误跳）
    - postMessage 失败回滚与截断游标推进的原子性（同轮要么回滚一致、要么推进一致）
- 实现以最小改动达成上述三点的方案自选（持久化字段 / identity 记账 / 回滚归并），但必须覆盖已确认的三类缺口。

### 非范围

- emitted key 粒度改会话维度（p166，独立 task t386）
- 日常数据量（远低于 MAX_RECORDS）下的性能优化
- collector 对外接口（IPC / scan-state 结构对外消费者）行为变更——持久化新增字段须兼容既有 scan-state

- [ ] AC-001：跨重启截断进度保留——单源超 `MAX_RECORDS`，首轮截断入列部分后重启 collector，后续轮从截断点继续推进，最终该源全部记录被扫描入列（对比修复前：重启后只重复发前 10000 条即停）。

- [ ] AC-004：既有 scan-state 兼容——升级后读取修复前的 scan-state 持久化数据不报错，扫描正常推进（新增字段有默认值或迁移）。
